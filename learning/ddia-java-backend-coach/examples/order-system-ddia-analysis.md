# 示例：用 DDIA 思想分析订单系统

## 1. 业务场景

用户下单，系统需要创建订单、扣减库存、发起支付，并在支付成功后更新订单状态。

## 2. 数据模型

核心表：order、order_item、inventory、payment、user。

## 3. 存储选择

核心订单和支付数据适合放在 MySQL / PostgreSQL，因为需要事务、约束和可靠持久化。

商品搜索可以放到 Elasticsearch。

热点商品库存可以放 Redis 做预扣或限流，但最终库存仍需要数据库或专门库存服务兜底。

## 4. 索引设计

常见查询：

- 根据 user_id 查询订单列表
- 根据 order_id 查询订单详情
- 根据 payment_id 查询支付状态
- 根据 product_id 查询库存

## 5. 事务边界

本地事务可以覆盖：创建订单、创建订单明细、初始化订单状态。

库存扣减和支付回调通常需要结合状态机、消息队列、幂等和补偿机制。

## 6. 一致性

订单系统通常不能全局强一致，否则性能和可用性会很差。

常用策略：核心状态本地事务保证；跨服务操作用最终一致性；MQ 传递领域事件；消费端幂等；定时任务对账补偿。

## 7. 故障场景

### 支付成功但订单更新失败

解决：支付回调幂等、支付成功事件落库、定时对账、重试更新订单状态。

### MQ 重复消费

解决：业务唯一键、消费记录表、状态机判断、幂等更新。

### 库存超卖

解决：数据库行锁、乐观锁版本号、Redis 预扣 + 异步确认、库存服务串行化处理。

## 8. DDIA 对应知识

- ch3：索引与存储
- ch5：复制与读写分离
- ch6：分区与分库分表
- ch7：事务与隔离
- ch8：超时、重试、幂等
- ch11：消息队列与事件流
