# 示例：缓存一致性分析

## 问题

Java 后端系统中经常使用 Redis 缓存 MySQL 数据。问题是：数据库更新后，缓存如何保持一致？

## DDIA 视角

缓存是派生数据。派生数据不是权威数据源，而是从数据库派生出来的读优化视图。

因此缓存一致性问题，本质是：

```text
权威数据源变化后，派生数据如何同步更新？
```

## 常见方案

### 1. 先更新数据库，再删除缓存

优点：简单、常用。

风险：删除缓存失败；并发读导致旧值回填。

### 2. 延迟双删

流程：删除缓存 → 更新数据库 → 延迟一段时间再删除缓存。

风险：延迟时间不好确定；不是严格一致。

### 3. 通过 MQ / CDC 更新缓存

流程：数据库变更 → 产生 binlog / 事件 → 消费者更新或删除缓存。

优点：解耦，适合多种派生数据同步。

风险：消息延迟、消息重复、消息丢失、消费失败。

## Java 后端实践建议

- 默认把数据库作为权威数据源
- 缓存只做性能优化，不承载核心一致性
- 更新数据库后优先删除缓存，而不是更新缓存
- 消费端必须幂等
- 重要业务增加对账和补偿
